# ADR: Student Registry — StudentProfile and GuardianProfile Field Classification

**Status:** Approved  
**Date:** 15 August 2026  
**Prepared for:** Student Registry and Enrolment release  
**Author:** Implementation team  

---

## Context

`StudentProfile` extends the permanent `Person` identity (name, birth date, identifiers, contact points) with student-specific operational and welfare information. The specification requires that no medical diagnoses or counselor notes are placed directly on `StudentProfile`, and that all sensitive fields carry explicit field-level permission.

`GuardianProfile` extends `Person` for guardian-role purposes and may optionally link to a `GuardianAccount`.

This ADR classifies every proposed field and records the approved visibility tier and required permission for each.

---

## StudentProfile Fields

### Core identity fields (non-duplicating Person)

| Field | Type | Nullable | Description |
|---|---|---|---|
| `id` | BIGINT unsigned | No | Surrogate primary key |
| `student_code` | VARCHAR(32) | No | Stable unique human-readable code (e.g. STU-2026-00001). Never the national ID. |
| `person_id` | BIGINT unsigned | No | FK to `people.id` (RESTRICT, unique) |
| `lifecycle_status` | VARCHAR(32) | No | See lifecycle states below |
| `registered_on` | DATE | No | Date the student profile was first registered in the system |
| `created_at` | TIMESTAMP | No | |
| `updated_at` | TIMESTAMP | No | |

`student_code` is excluded from `$fillable`; generated by `CreateStudentProfile` action using a configurable prefix and sequential counter per institution or globally.

### Welfare and social fields

| Field | Type | Nullable | Visibility | Required permission |
|---|---|---|---|---|
| `orphan_status` | VARCHAR(32) | Yes | Institution staff + Counselor + Principal | `student.view_restricted` |
| `displacement_status` | VARCHAR(32) | Yes | Institution staff + Counselor + Principal | `student.view_restricted` |
| `displacement_location` | VARCHAR(255) | Yes | Institution staff + Counselor + Principal | `student.view_restricted` |
| `family_member_count` | SMALLINT unsigned | Yes | Institution staff + Counselor + Principal | `student.view_restricted` |
| `family_order` | TINYINT unsigned | Yes | Institution staff + Counselor + Principal | `student.view_restricted` |
| `accessibility_indicator` | BOOLEAN | Yes | Institution staff + Counselor + Principal + Guardian-visible when permitted | `student.view` (indicator only); full note requires `student.view_restricted` |

**Rationale for `student.view_restricted`:**
- Orphan and displacement status are sensitive welfare data that could affect a student's safety or family situation if disclosed inappropriately.
- Family count and order are useful for counselor and administrative purposes but are not routine administrative fields.
- `accessibility_indicator` is a boolean flag (does this student have an accessibility accommodation need?) visible to all institution staff so they can make reasonable adjustments. The underlying detail of the accommodation, if any, is a future protected record in the Welfare module.

### Fields explicitly excluded from StudentProfile

| Excluded field | Reason | Correct location |
|---|---|---|
| Full name, birth date | Already on Person | `people` table |
| National ID | Already on Person via PersonIdentifier | `person_identifiers` table |
| Phone, email | Already on Person via ContactPoint | `contact_points` table |
| Medical diagnoses | Sensitive clinical data; requires Medical module | Future `health_conditions` table |
| Counselor notes | Restricted welfare data | Future `counselor_notes` table |
| Current enrollment, class, grade | Semester-specific; changes each year | `student_enrollments` table |
| Photograph | Not in scope for this release | Future media attachment |
| HR/finance data | Not applicable to students | Separate HR domain |

## StudentProfile Lifecycle States

| State | Meaning | Allowed transitions |
|---|---|---|
| `draft` | Profile created but not yet verified/activated | → active |
| `active` | Student is currently enrolled or eligible for enrollment | → inactive, withdrawn, graduated, deceased |
| `inactive` | Temporarily not enrolled; record preserved | → active |
| `withdrawn` | Formally withdrawn from all GCV institutions | → active (re-registration) |
| `graduated` | Completed final level; terminal state normally | No further transitions expected |
| `deceased` | Student has died; record preserved for historical accuracy | No further transitions |

**Rules:**
- Lifecycle transitions require an explicit action with an actor reference and optional reason.
- `withdrawn`, `graduated`, and `deceased` states are terminal for normal operations; only authorized administrators may make further changes.
- A student in `draft` state may be enrolled in a draft enrollment but not an active enrollment.
- `deceased` status is never set automatically from civil-registry data (the civil registry `is_deceased` field is advisory only).

## GuardianProfile Fields

| Field | Type | Nullable | Description |
|---|---|---|---|
| `id` | BIGINT unsigned | No | Surrogate primary key |
| `guardian_code` | VARCHAR(32) | No | Stable unique code (e.g. GRD-2026-00001) |
| `person_id` | BIGINT unsigned | No | FK to `people.id` (RESTRICT, unique) |
| `lifecycle_status` | VARCHAR(32) | No | `active` / `inactive` / `deceased` |
| `guardian_account_id` | BIGINT unsigned | Yes | Optional FK to `guardian_accounts.id` (SET NULL on delete) |
| `created_at` | TIMESTAMP | No | |
| `updated_at` | TIMESTAMP | No | |

**Rules:**
- `GuardianProfile` does not automatically create a `GuardianAccount`. Account creation is a separate explicit action.
- `guardian_account_id` being set does not grant student access; active verified portal-eligible `GuardianStudentRelationship` records are required.
- `guardian_code` excluded from `$fillable`; generated by `CreateGuardianProfile` action.

## GuardianStudentRelationship Fields

| Field | Type | Nullable | Description |
|---|---|---|---|
| `id` | BIGINT unsigned | No | Surrogate PK |
| `student_profile_id` | BIGINT unsigned | No | FK to `student_profiles.id` (RESTRICT) |
| `guardian_profile_id` | BIGINT unsigned | No | FK to `guardian_profiles.id` (RESTRICT) |
| `relationship_type` | VARCHAR(32) | No | See relationship types below |
| `legal_authority` | VARCHAR(32) | No | `full`, `limited`, `none`, `unknown` |
| `verification_status` | VARCHAR(32) | No | `unverified`, `pending`, `verified`, `rejected` |
| `portal_eligible` | BOOLEAN | No | Default false; set explicitly by authorized staff |
| `contact_priority` | TINYINT unsigned | Yes | Lower = higher priority |
| `is_emergency_contact` | BOOLEAN | No | Default false |
| `starts_on` | DATE | Yes | When this relationship began |
| `ends_on` | DATE | Yes | When this relationship ended (null = ongoing) |
| `restricted_notes` | TEXT | Yes | Visible to counselor and principal only; requires `guardian_relationship.view` with restricted flag |
| `evidence_status` | VARCHAR(32) | Yes | `none`, `pending`, `received`, `verified`, `rejected` |
| `evidence_reference` | VARCHAR(255) | Yes | Reference to attached document (future Attachments module) |
| `history_metadata` | JSON | Yes | Correction history summary |
| `created_at` | TIMESTAMP | No | |
| `updated_at` | TIMESTAMP | No | |

**Relationship types:** `father`, `mother`, `legal_guardian`, `grandparent`, `sibling`, `relative`, `foster_carer`, `representative`, `other`

**Portal eligibility rules:** requires `verification_status = 'verified'` AND `portal_eligible = true` AND `ends_on IS NULL` (or `ends_on >= today`). All three conditions must hold.

**Historical preservation:** When a relationship ends, `ends_on` is set. The row is never deleted. A new row is created for any replacement relationship.

---

## Decision: No Automatic Guardian Access from National ID Match

The civil-registry may return a `father_national_id` or `mother_national_id`. These IDs are presented as possible follow-up lookups only. Matching national IDs do not automatically:
- Create a GuardianProfile
- Create a GuardianStudentRelationship
- Grant portal access

Each of these steps requires explicit authorized staff action.

## Open Questions (Not Blocking Implementation)

1. Whether `family_member_count` and `family_order` should be versioned/dated as they can change (e.g. a new sibling is born). Current decision: single mutable field with correction history in the Audit module.
2. Exact accessibility indicator detail format — deferred to Welfare module.
3. Whether `displacement_location` is a free-text field or references a location catalogue. Current decision: free text with validation guidelines, location catalogue deferred.

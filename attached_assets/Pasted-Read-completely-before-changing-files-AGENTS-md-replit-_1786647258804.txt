TERMINOLOGY

Distinguish between:

1. Physical Laravel packages managed by `nwidart/laravel-modules`, such as
   Modules/Organization and Modules/Staff.
2. Configurable GCV business capabilities, such as academic management and
   inventory management.

In code and database naming, use `FeatureModule` / `feature_modules` or an
equally explicit existing convention that avoids collision with Nwidart's
`Module` concept.

The user-facing product may later label these capabilities “Modules.”

OWNERSHIP

- The Organization module owns feature-module definitions and institution-type
  feature rules.
- Do not create a new physical Laravel module.
- F05 configures institution-type capabilities only.
- Institution-specific overrides belong to F06 and must not be implemented.

APPROVED RULE SEMANTICS

Every institution-type/feature relationship has exactly one rule:

- `required`
  - enabled by default;
  - a future F06 institution override may not disable it.

- `default`
  - enabled by default;
  - a future F06 institution override may disable it.

- `allowed`
  - disabled by default;
  - a future F06 institution override may enable it.

- No rule:
  - the feature is unavailable to that institution type;
  - F06 must not allow an institution to enable it.

Do not use a database ENUM.

A closed PHP value object or backed enum may represent these three rule values
inside application code if consistent with current conventions. Persist as a
bounded string and enforce valid values at application and database levels
where MySQL/MariaDB and SQLite compatibility can be maintained safely.

FEATURE-MODULE MODEL

Create a module-owned model/table with:

- unsigned BIGINT internal primary key;
- immutable stable unique `code`;
- required `name_en`;
- nullable `name_ar`;
- `is_active` boolean, active by default;
- Laravel timestamps;
- no soft deletion;
- no database ENUM;
- no partial actor-audit columns.

`is_active` is lifecycle/configuration availability, not authorization and not
proof that the business feature has already been implemented.

INSTITUTION-TYPE RULE MODEL

Create a module-owned relationship model/table with:

- unsigned BIGINT internal primary key unless existing conventions justify a
  composite-only pivot;
- foreign key to institution_types;
- foreign key to feature_modules;
- bounded rule value: required, default, or allowed;
- Laravel timestamps if treated as an administratively managed entity;
- a unique constraint on institution_type_id + feature_module_id;
- restrictive foreign-key behavior that does not erase historical
  configuration accidentally;
- no soft deletion;
- no actor-audit fields yet.

Prefer an explicit rule model over a featureless `belongsToMany` pivot because
the relationship has behavior and will later participate in F06 resolution.

RELATIONSHIPS

Add composable relationships such as:

- InstitutionType has many feature-module rules.
- FeatureModule has many institution-type rules.
- A rule belongs to one InstitutionType and one FeatureModule.

Convenient many-to-many traversal may be added only if it does not hide the
rule semantics.

Do not attach feature modules directly to institutions in F05.

REQUIRED ACTIONS/SERVICES

Add request-independent application behavior for:

- creating a feature-module definition;
- changing bilingual display names;
- activating/deactivating a feature-module definition;
- assigning or changing an institution-type rule;
- removing a rule only through an explicit action if removal is approved as

Stable feature codes must not be changed by ordinary updates.

Actions must not expose an allow-all authorization implementation. Future HTTP
callers will require the F17/F19 policy kernel.

Do not build HTTP routes or UI.

SEEDING

Create idempotent seeding for:

- the six feature-module definitions;
- the approved institution-type rules.

Seeder requirements:

- create missing definitions and rules;
- create rules only against the approved stable institution-type codes;
- preserve administrator-edited feature display names;
- preserve feature lifecycle state;
- do not reset an existing rule silently if an administrator changed it;
- report or test drift rather than silently overwriting it;
- create no duplicates when rerun;
- connect deliberately to the normal root/module seeding process;
- remain safe under repeated `migrate:fresh --seed`.

Do not rely on display names for matching.

RESOLUTION BOUNDARY

F05 may provide a pure baseline rule interpreter that answers questions such
as:

- Does this type require the feature?
- Is it enabled by type default?
- Is the type allowed to activate it later?
- Is the feature unavailable to this type?

However:

- Do not implement institution-specific overrides.
- Do not create InstitutionModuleActivation.
- Do not register an OperationalScopeAuthorizer.
- Do not add route middleware.
- Do not claim that a configured feature grants permission.
- Do not claim that a planned feature is implemented merely because a
  definition exists.
- The complete institution resolver belongs to F06.

If a baseline interpreter is added, its expected results are:

- required → baseline enabled, cannot disable;
- default → baseline enabled, may disable later;
- allowed → baseline disabled, may enable later;
- no rule → baseline disabled, cannot enable.

LIFECYCLE RULES

- Inactive FeatureModule records remain queryable historically.
- Inactive definitions cannot be newly assigned to types through ordinary
  application behavior.
- Deactivation does not delete type rules.
- Existing rules pointing to an inactive definition remain inspectable.

- Stable codes remain immutable.
- Deleting definitions or rules through ordinary Eloquent deletion should be
  prevented or avoided according to existing module conventions.

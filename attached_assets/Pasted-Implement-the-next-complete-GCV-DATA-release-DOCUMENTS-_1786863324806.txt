2. SHARED WORKFLOW ENGINE
==================================================

Implement a constrained state-machine workflow engine.

WorkflowDefinition must be stable and code-governed.

Initial workflow types:

- student_correction
- student_document
- institution_formal_request
- sensitive_identity_correction
- guardian_relationship_correction
- student_transfer_approval
- result_publication_approval where integration is appropriate

WorkflowInstance must include:

- Definition code/version
- Typed subject reference
- Current state
- Initiating actor and portal
- Organization/institution scope
- Institution-semester scope where relevant
- Assigned/responsible actor or role
- Due date, nullable
- Correlation ID
- Created/completed timestamps

WorkflowAction must append:

- Previous state
- New state
- Action code
- Actor/account/portal
- Decision/comment
- Safe metadata
- Timestamp

Rules:

- State transitions are explicit.
- Unknown transitions fail.
- Workflow rows are historical and not overwritten.
- Role name alone does not authorize an action.
- Every transition rechecks account, permission, assignment, institution, semester, period, and record state.
- Cross-institution workflows are denied.
- Completed/cancelled workflows are immutable except through explicit reopen/supersession actions.
- Required audit failure rolls back the transition.
- Concurrent decisions cannot approve the same step twice.

Do not let clients submit arbitrary subject class names or workflow definitions.

3. SECURE ATTACHMENTS
==================================================

Implement private file attachments.

Fields/concepts:

- Opaque ID
- Original filename
- Safe generated storage name
- MIME type
- Extension
- Size
- SHA-256 hash
- Private disk/path
- Uploader actor/account/portal
- Organization/institution scope
- Classification
- Created timestamp
- Quarantine/available/rejected state

Rules:

- Store outside public web directories.
- Downloads pass through authorized controllers/services.
- Never trust client MIME type or filename.
- Sanitize displayed filenames.
- Validate size, extension, detected MIME, and expected request purpose.
- Deny executable/script formats.
- Use allowlists per workflow.
- Prevent path traversal.
- Never render uploaded HTML as trusted application content.
- Detect duplicate files by hash where useful without leaking cross-scope existence.
- Attachments remain linked to immutable request history.
- Removing an attachment from an active view must not erase required historical evidence.
- Virus-scanner integration may use a contract if no scanner exists in the environment; unscanned files must be clearly classified according to policy.

Initial allowed evidence formats:

- PDF
- JPG
- JPEG
- PNG

Office files require a separate explicit allowlist and safe download behavior.

4. GUARDIAN STUDENT-CORRECTION REQUESTS
==================================================

Implement StudentCorrectionRequest.

Guardian workflow:

1. Guardian selects an accessible student.
2. Chooses the record/field requiring correction.
3. Enters proposed value and explanation.
4. Adds supporting evidence where appropriate.
5. Submits.
6. Secretary reviews.
7. Secretary accepts, rejects, or requests clarification.
8. Sensitive changes require principal/deputy or data-administrator approval.
9. Approved change is applied through the owning domain action.
10. Guardian receives the decision.
11. Original request, proposed value, evidence, decisions, and applied change remain historical.

States:

- draft
- submitted
- clarification_requested
- resubmitted
- under_review
- approved
- rejected
- applied
- cancelled
- superseded

Rules:

- Guardian may request correction only for an actively accessible student.
- Guardian never edits official records directly.
- The request stores a typed field/change proposal, not an arbitrary model/table/column name.
- Supported correctable field catalogue is code-governed.
- Sensitive identifiers and guardian/legal relationships require enhanced approval.
- Requested and official values are stored/protected according to field classification.
- Public notifications do not expose proposed sensitive values.
- Applying a correction is atomic and auditable.
- If official data changed during review, flag a conflict and require re-review.
- Rejection and clarification require comments.
- Applied corrections cannot be silently reversed.

Initial requestable areas:

- Basic student/person spelling
- Birth-date correction
- Contact correction
- Address/displacement information
- Guardian relationship information
- Identifier correction through the existing protected identity workflow

Do not allow guardian-requested medical or counselor-note changes through this general workflow.

Each DocumentType defines:

- Required data completeness checks
- Approval requirement

Workflow:

3. Missing data returns request for clarification/correction.

5. System generates an immutable document.
6. Requester receives an in-app notification.
7. Authorized requester downloads the issued copy.

States:

- draft
- submitted
- under_review
- clarification_requested
- ready_for_approval
- approved
- rejected
- generating
- issued
- generation_failed
- cancelled
- superseded

A document request does not itself alter student data.

6. FORMAL INSTITUTION REQUESTS
==================================================

Implement InstitutionFormalRequest.

Workflow:

1. Secretary prepares a draft.
2. Principal/deputy reviews.
3. Principal/deputy signs and submits.
4. Central management reviews.
5. Central management accepts, rejects, returns, or responds.
6. Institution tracks the result and response.

Fields/concepts:

- Stable request number
- Institution
- Institution semester, optional
- Request type
- Arabic/English title
- Structured body/content
- Due date
- Priority
- Responsible actor
- Attachments
- Comments
- Current state
- Version/content hash
- Response
- Status history

States:

- draft
- internal_review
- returned_to_preparer
- signed
- submitted_to_management
- under_management_review
- clarification_requested
- accepted
- rejected
- responded
- closed
- cancelled
- superseded

Rules:

- Secretary cannot sign as principal.
- Central read permission does not automatically allow decisions.
- Institution cannot alter a request after signature/submission.
- Returned request creates a new editable version while preserving the signed version.
- All comments identify actor and audience.
- Restricted internal comments are not visible to guardians or unrelated staff.
- Requests use electronic signatures, not fake image signatures.

7. ELECTRONIC APPROVAL AND SIGNATURE
==================================================

Implement audited ElectronicApproval.

Capture:

- Approver account and portal
- Approval type
- Decision
- Exact subject/version
- Canonical content hash
- Timestamp
- Comment
- Reconfirmation method
- Revoked/superseded state
- Safe request/device fingerprint where lawful

For sensitive/signing actions:

- Require recent authentication or password reconfirmation.
- Use the correct portal guard.
- Rate-limit failed reconfirmation.
- Never log or store submitted passwords.
- Regenerate/reprotect session state where appropriate.
- Reject approval if content changed after confirmation.
- Distinguish verifier, approver, signatory, and publisher.

An electronic signature is an auditable system confirmation. Do not claim certificate-based legal cryptographic signing.

Certificate-backed digital signatures remain a future integration unless an approved certificate/provider is supplied.

==================================================

Example structure:

GCV-{TYPE}-{YEAR}-{SEQUENCE}

Public verification:

- Use a high-entropy opaque verification code.
- Store a secure hash if possible.
- Do not expose sequential database IDs.
- Rate-limit lookup.
- Show only minimal safe information:
  - Valid/invalid/cancelled status
  - Document type
  - Document number
  - Issuing institution
  - Issue date
- Do not expose student name, national ID, birth date, marks, attendance, or document file publicly.
- Full download still requires authentication and authorization.

Provide authenticated verification with more information only when authorized.

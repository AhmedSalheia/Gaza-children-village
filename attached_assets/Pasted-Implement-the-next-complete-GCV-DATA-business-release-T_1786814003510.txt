2. TEACHING ASSIGNMENTS
==================================================

Implement TeachingAssignment.

It must link:

- Active teacher StaffPosition
- StaffProfile
- InstitutionSemester
- ClassGroup
- InstitutionSubjectOffering
- Effective dates/status

Relationship rules:

- Staff position, assignment, institution semester, class, period, and subject offering must belong to the same institution context.
- The staff position must be an eligible teacher/trainer position.
- A teacher role by itself grants no teaching access.
- A subject assignment grants no access to unrelated classes.
- A class assignment grants no access to unrelated subjects.
- Closed/archived semesters reject ordinary assignment mutation.
- Overlapping duplicate assignments are rejected.
- Historical assignments remain readable.
- Staff transfers immediately stop access through the old institution assignment.

Implement HomeroomAssignment separately.

It must link an eligible teacher position to a ClassGroup and effective interval.

Rules:

- Homeroom assignment permits student-attendance entry for that class.
- It does not grant mark access without a matching TeachingAssignment.
- A class may have one active lead/homeroom teacher unless an explicit co-lead assignment is approved.
- Co-lead support must be explicit, not accidental duplicate assignments.

Provide actions for create, end, replace, list, and resolve assignments for a trusted operational context.

6. QR-ASSISTED STAFF ATTENDANCE
==================================================

Implement reviewable QR attendance as an input method.

QR security:

- Do not encode sequential StaffProfile IDs alone.
- Use a random, revocable, rotatable credential.
- Store only a secure token hash.
- Display token plaintext only when generating the QR.
- Credentials have active/revoked lifecycle and issue history.
- Never log raw QR tokens.
- Rate-limit scan submission.
- Prevent replay from creating duplicate official attendance.

Create AttendanceScanEvent containing:

- Safe QR credential reference
- Institution/period context
- Scan timestamp
- Scan direction candidate: arrival/departure/unknown
- Device/request fingerprint where lawful
- Processing status
- Matched StaffProfile
- Reviewer
- Review outcome

Workflow:

1. QR is scanned.
2. Token is validated.
3. Context is validated.
4. A pending scan event is recorded.
5. Secretary reviews/matches arrival or departure.
6. Accepted value becomes a scanned candidate.
7. Authorized verification confirms the official attendance value.

QR scans never directly create verified attendance.

Provide:

- Branded staff QR-card generation
- Individual and role-filtered bulk generation
- PNG/PDF-friendly layout
- GCV logo and design tokens
- Manual token input fallback
- Camera scanner only if it performs acceptably with existing frontend architecture

Do not add heavy OpenCV.js loading to ordinary pages. If camera detection is implemented, lazy-load it only on the scanner page and retain a lightweight fallback.

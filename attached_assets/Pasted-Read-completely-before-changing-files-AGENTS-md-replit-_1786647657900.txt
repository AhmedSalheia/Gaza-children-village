APPROVED RESOLUTION SEMANTICS

For an active institution and active feature definition:

1. Type rule `required`
   - effective state: enabled;
   - source: required;
   - institution cannot disable it;
   - institution-specific overrides are rejected.

2. Type rule `default`
   - effective state: enabled without an override;
   - an institution may explicitly disable it;
   - clearing the override restores enabled-by-default behavior;
   - a redundant enabled override should be rejected rather than stored.

3. Type rule `allowed`
   - effective state: disabled without an override;
   - an institution may explicitly enable it;
   - clearing the override restores disabled-by-default behavior;
   - a redundant disabled override should be rejected rather than stored.

4. No type rule
   - effective state: disabled and unavailable;
   - the institution cannot enable it;
   - override creation is rejected.

5. Inactive FeatureModule
   - effective state: disabled;
   - existing configuration remains inspectable;
   - no new override may be created or changed through ordinary actions.

6. Inactive Institution
   - operational effective state: disabled;
   - configuration remains inspectable for administration/history;
   - no new override may be created or changed through ordinary actions.

7. Inactive InstitutionType
   - does not erase rules from already-existing institutions;
   - existing institutions continue resolving against their assigned type;
   - inactivity prevents ordinary new use of the type elsewhere, as already
     defined by F03/F04.

Configuration availability is not authorization.

OVERRIDE MODEL

Create an explicit module-owned model/table such as
`institution_feature_overrides`, using the existing naming conventions.

Required fields:

- unsigned BIGINT internal primary key;
- foreign key to institutions;
- foreign key to feature_modules;
- `is_enabled` boolean;
- nullable textual `reason`;
- Laravel timestamps;
- unique institution_id + feature_module_id;
- no soft deletion;
- no actor-audit columns yet;
- no database ENUM.

Use restrictive foreign-key behavior. Deleting an institution or feature must
not cascade-delete configuration silently.

Only meaningful override rows are permitted:

- default rule → `is_enabled = false`
- allowed rule → `is_enabled = true`

Do not store override rows for:

- required rules;
- unavailable/no-rule features;
- default → true;
- allowed → false.

Clearing an override restores inheritance from the institution type.

Current-state overrides are approved for F06 to keep implementation bounded.
Effective date scheduling, approval workflows, and immutable configuration
history remain deferred. Document this explicitly. Future Audit integration
must capture override creation/removal and reasons before management UI is
released.

RESOLUTION RESULT

resolver.

It should expose at least:

- institution reference;
- feature reference/code;
- effective enabled state;
- availability state;
- resolution source;
- whether the institution may enable it;
- whether the institution may disable it;
- whether an override currently exists;
- a stable reason/key suitable for logs and future UI.

Recommended resolution sources:

- `required`
- `type_default`
- `institution_override`
- `allowed_but_disabled`
- `unavailable`
- `feature_inactive`

F16 — SEMESTER POSITIONS AND PERIOD SCOPES
==================================================

Implement in Modules/Staff:

- PositionDefinition
- StaffPosition
- StaffPositionPeriod

Reuse:

- StaffProfile
- StaffInstitutionAssignment
- Institution
- InstitutionSemester
- OperationalPeriod
- F02 operational context
- F06 module activation

Initial controlled position definitions:

- principal
- deputy_principal
- secretary
- teacher
- counselor
- trainer
- medical_staff
- women_center_staff
- storage_staff
- guard
- general_staff

Position names do not grant permissions by themselves.

Rules:

- Every StaffPosition belongs to an active StaffProfile and a valid StaffInstitutionAssignment.
- The assignment and position must reference the same institution.
- Academic-institution positions reference an InstitutionSemester.
- Non-academic institution positions may be institution-wide without an InstitutionSemester.
- A position referencing an InstitutionSemester must fall within the assignment’s institution and effective dates.
- Closed or archived institution semesters reject ordinary position mutation.
- Historical positions remain readable.
- StaffPosition creation never creates an account.
- Guards and other non-login staff may have complete position history.
- Teacher/trainer positions grant no class, course, subject, student, or mark access.

Period scopes:

- Period-restricted positions use explicit StaffPositionPeriod rows.
- Every referenced period must belong to the position’s InstitutionSemester.
- No period ID supplied by a request is trusted without relationship resolution.
- A secretary may be assigned to one, several, or all periods.
- “All periods” must be represented explicitly by links to all currently approved periods; do not implement an implicit unrestricted wildcard.
- Adding a new period later does not silently expand existing staff access.
- A one-period secretary is denied access to every other period.
- Institution-wide non-academic positions cannot have period links.

Compatibility:

- Duplicate overlapping instances of the same position definition are rejected.
- Principal and deputy_principal are mutually exclusive for the same person during the same effective interval.
- Other distinct same-institution responsibilities may coexist initially.
- Acting/delegated positions and approval workflows remain deferred.
- Use effective dates and prevent invalid overlaps transactionally.

Provide actions/queries for:

- Assign position
- End position
- Replace position scopes
- Resolve active positions for a date/context
- List position history
- Determine whether a position covers a requested period

Tests must cover relationship chains, dates, concurrency, compatibility, historical reads, one-period denial, explicit all-period scope, non-login staff, and no inferred teaching access.

F17 — PERMISSION CATALOGUE AND POLICY KERNEL
==================================================

Create an ADR approving a first-party authorization kernel.

Do not install a broad roles/permissions package unless the existing repository already approved one.

Entities:

- Permission
- Role
- RolePermission
- AdministrativeAccountRole
- PositionRoleGrant

Do not add direct account permission overrides.

Authorization precedence:

1. Invalid/inactive portal account → deny
2. Wrong portal → deny
3. Missing required module → deny
4. Invalid organization/institution chain → deny
5. Missing active assignment/position → deny
6. Wrong semester/period → deny
7. Closed/archived mutation → deny
8. Missing explicit permission → deny
9. Otherwise allow

There is no implicit super-admin bypass.

Multiple valid roles combine granted permissions, but they never bypass scope, lifecycle, account state, module availability, or field classification.

Create stable Foundation permission keys for:

- Organization metadata read/manage
- Institution metadata read/manage/lifecycle
- Module configuration read/manage
- Academic calendar read/manage/lifecycle
- Institution semester read/manage/lifecycle
- Person basic read/manage
- Restricted identifier read/manage
- Contact read/manage/verify
- Staff profile read/manage
- Staff assignment read/manage/transfer
- Staff position read/manage
- Account read/manage/revoke sessions
- Audit read

Keep organization-wide read permissions separate from institution-owned mutation permissions.

Initial protected role templates:

Administrative:

- system_administrator
- data_administrator
- central_auditor

Staff-position roles:

- principal
- deputy_principal
- secretary
- teacher
- counselor
- trainer
- medical_staff
- women_center_staff
- storage_staff

Guardian access remains relationship-derived later and receives no staff-style role.

Important:

- `system_administrator` is still a permission bundle, not a domain bypass.
- Central data administrators may read authorized organization-wide records.
- Central read does not silently authorize institution-owned mutations.
- Teacher/trainer roles receive no student/class/subject permission yet.
- Unknown permissions and resources deny by default.
- Role codes and permission codes are stable and code-governed.
- Display labels use translation keys.

Add:

- AuthorizationDecisionContext
- Policy decision/result type
- Denial reason codes safe for internal diagnostics
- Query-scope contracts
- Policy-kernel service
- Module/lifecycle/scope constraint evaluators

Public responses must not disclose inaccessible record existence.

Test every precedence rule and central-read/local-mutate separation.

F18 — APPEND-ONLY AUDIT INFRASTRUCTURE
==================================================

Implement a first-party Audit module.

Do not adopt a package or create ordinary mutable audit records.

AuditEvent must capture:

- Immutable event ID
- Actor type/reference
- Portal
- Source: web, job, CLI, import, system
- Action key
- Subject type/reference
- Organization, institution, institution-semester and period references where applicable
- Safe before/after changes
- Required reason where applicable
- Request/correlation ID
- Occurred timestamp
- Safe metadata
- Schema/version marker

Rules:

- Append-only in application code.
- Add database-level protection against ordinary UPDATE and DELETE where safely supported.
- No model update/delete API.
- No audit editing UI.
- No ordinary purge operation.
- Retention is indefinite during Foundation until legal retention rules are approved.
- Cryptographic hash chaining/tamper sealing is deferred; document this explicitly.
- Database access, backups, and administrator privileges remain infrastructure trust boundaries.

Redaction:

- Never store passwords, recovery tokens, session IDs, cookies, encryption keys, raw national IDs, raw passport IDs, or raw contact values.
- Sensitive before/after fields use classification-aware redaction.
- Prefer IDs and masked values.
- Omit raw IP addresses by default.
- If request-source correlation is needed, use a keyed privacy-preserving fingerprint.
- Do not store full user-agent strings unless explicitly justified.

Transaction behavior:

- Required audit creation participates in the same business transaction.
- If required audit persistence fails, the protected mutation rolls back.
- Audit writes cannot be disabled by an ordinary actor.
- Reads require explicit audit permission and scope.
- Audit access is read-only.
- Cross-institution audit access defaults to denied.

Integrate without rewriting F10:

- Keep AuthenticationEvent as its specialized Accounts-owned security stream.
- Provide a read/projection adapter so authorized audit inspection can include authentication security events.
- Do not duplicate secrets or copy raw credential data.
- Do not destructively migrate working F10 events unless required and proven safe.

Create framework-independent AuditRecorder and AuditReader contracts.

Tests must prove immutability, rollback-on-failure, redaction, portal/source distinction, scope restrictions, and authentication-event projection.

F20 — LOCALE ROUTING AND PREFERENCES
==================================================

Approved locale decisions:

- Supported locales: Arabic (`ar`) and English (`en`)
- Default locale: Arabic
- Fallback locale: English
- Operational timezone: Asia/Gaza
- Store timestamps in UTC and render in the operational timezone
- Use Gregorian calendar
- Use day-month-year presentation
- Use Latin digits for identifiers, dates, codes, and data-entry consistency in both locales
- Prefer locale-specific name when available, falling back to Arabic and then the stable code
- Static interface copy uses Laravel language files
- Do not create a translation database for static copy

Locale preference:

- Authenticated accounts persist their preference on their own account table.
- Unauthenticated pages use a portal-safe session preference.
- Locale switching must not change authentication or operational context.
- Add a POST locale-switch action with CSRF protection.
- Validate against the exact supported-locale list.
- Invalid locale values fall back safely.
- Avoid open redirects after switching.

Translate all current Foundation-facing text, including:

- Login/logout
- Validation
- Authentication failures
- Throttling
- Empty/error states
- Portal names
- Lifecycle labels
- Account states
- Institution terminology
- Permission-denied messages

Anti-enumeration responses must remain semantically identical across locales.

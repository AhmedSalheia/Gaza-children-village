NEW FUTURE REQUIREMENT 1 — EXCEL IMPORTS

The future import engine must support explicitly selected modes:

1. `insert_only`
   - Create rows that do not already exist according to an approved stable
     matching key.
   - Skip matching existing records.
   - Report every created, skipped, and invalid row.

2. `patch_existing`
   - Match existing records using an approved stable matching key.
   - Update only explicitly permitted/importable fields.
   - Skip rows with no existing match.
   - Report old/new proposed values before commitment.

Do not call insert-only behavior “patch importing” in technical documentation.

All future imports must use:

- uploaded-file registration;
- staged rows;
- schema/header validation;
- normalized matching keys;
- duplicate detection within the file;
- preview/dry run;
- row-level errors and warnings;
- explicit confirmation before official writes;
- transactional or recoverable batches;
- idempotency protection;
- import actor and scope;
- created/skipped/updated/failed counts;
- downloadable result report;
- institution, semester, period, permission, and field-level enforcement;
- no direct unreviewed Excel-to-production-table writes.

Do not create import tables, services, routes, jobs, or modules in F03.

NEW FUTURE REQUIREMENT 2 — GAZA CIVIL-REGISTRY LOOKUP

When an authorized user registers a student in a later Student module:

1. The user enters the student’s national ID.
2. The ID is normalized and validated.
3. The system queries the Gaza civil-registry reference source through a
   deliberate application contract/service.
4. A matching registry record may suggest/autofill approved identity fields.
5. The user reviews the suggestions before saving the student.
6. The civil-registry source is advisory, not unquestionable authority.
7. A missing match must not prevent authorized manual student registration.
8. A registry match must not automatically overwrite an existing person or
   student.
9. Conflicting data must be shown for review and handled through a controlled
   correction/identity-resolution workflow.
10. The student uses a stable synthetic internal primary key. National ID is
    an identifier, not the Student table primary key.
11. National IDs and registry data are sensitive and require masking,
    permission controls, safe logging, and audit redaction.
12. The system should preserve data provenance where useful: registry-
    suggested, user-entered, imported, or later corrected.
13. The future Student module must not couple itself directly to a raw registry
    table throughout the codebase; use a stable lookup contract and adapter.
14. Do not assume the final physical table name is
    `gaza_civil_records`. Record the exact source/table naming as unresolved
    until the existing dataset/schema is reviewed.

Do not create civil-registry migrations, models, adapters, student tables,
lookup endpoints, or registration UI in F03.

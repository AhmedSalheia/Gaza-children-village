==================================================
1. APPROVED F09 ARCHITECTURE DECISIONS
==================================================

Record these decisions in an Authentication Account Topology ADR before implementation.

A. Physical account topology

Use three separate account models and database tables:

- AdministrativeAccount
- StaffAccount
- GuardianAccount

Each account type has its own:

- Eloquent authentication provider
- Session guard
- Password broker configuration
- Authentication middleware boundary
- Route namespace and route-name prefix
- Protected portal layout
- Account factory for synthetic tests

Do not use a single polymorphic users table.

B. Portal mapping

- Admin Portal → AdministrativeAccount → `admin` guard
- Staff Portal → StaffAccount → `staff` guard
- Parent/Student Portal → GuardianAccount → `guardian` guard

“Parent/Student Portal” remains the user-facing name, but the authenticated account belongs to a parent or authorized guardian, never to a student.

C. Login identifiers

- Administrative accounts use a normalized unique username.
- Staff accounts use a normalized unique username.
- Guardian accounts use an opaque normalized `login_identifier`.

The final guardian experience is intended to accept a national ID, but F09 must not store a permanent civil identity fact directly on an account.

Future F11/F13 work will resolve submitted guardian national IDs through approved person-identifier records into the guardian account.

Do not add national-ID columns to account tables in F09.

D. Account/profile cardinality

- Staff and guardian account existence is optional.
- Creating a staff/person record must never automatically create an account.
- Eventually, each staff or guardian profile may have at most one account of its corresponding portal type.
- A person may hold different portal account types when legitimately needed.
- StaffProfile and Person do not exist yet; do not start F13 or F15 merely to add these links.
- Add the profile foreign keys later, in their owning Foundation PRs.

E. Account lifecycle

Use one centralized account-state value object/enum shared by the account models:

- pending
- active
- suspended
- locked
- revoked

Only `active` accounts can authenticate or retain an authenticated session.

Definitions:

- pending: provisioned but not activated
- active: authentication permitted
- suspended: temporarily denied administratively
- locked: denied because of a security decision
- revoked: permanently disabled unless a future explicitly approved recovery rule says otherwise

Do not implement automatic lockout thresholds in F09.

Lifecycle checks must be enforced centrally, not independently inside controllers.

F. Decisions deferred

Do not decide or implement:

- Automatic lockout thresholds
- Login rate limits
- Concurrent-session policy
- MFA or PIN authentication
- Password setup/reset delivery
- Guardian verification evidence
- Guardian-student eligibility
- Administrative provisioning UI
- Authentication audit events
- Session-revocation workflows

These belong to F10, F11, or later decision gates.

3. DATABASE STRUCTURE
==================================================

Create separate tables for:

- administrative_accounts
- staff_accounts
- guardian_accounts

Each table should contain only the credential/account facts required by F09:

- id
- normalized unique login identifier
- password
- status
- activated_at, nullable
- suspended_at, nullable
- locked_at, nullable
- revoked_at, nullable
- timestamps

Use:

- `username` for administrative and staff accounts
- `login_identifier` for guardian accounts

Rules:

- Identifiers must be normalized consistently.
- Identifier uniqueness is portal-local, not global across all account types.
- Passwords must always be hashed through a centralized model cast/service.
- Passwords must be hidden from arrays, JSON serialization, logs, exceptions, and debug output.
- Do not use database enums.
- Do not add soft deletion.
- Do not add fake audit columns before F18.
- Do not add person_id, staff_profile_id, student_id, or national_id yet.

Handle the default Laravel User scaffold safely:

- Remove it as an authentication authority.
- Remove generic `users` provider/guard assumptions from authentication configuration.
- Do not destructively drop an existing table containing real data.
- If the unused default users table remains for migration compatibility, document it clearly as deprecated and prove that no guard/provider references it.
- Do not silently migrate generic users into one of the three account types.

4. AUTHENTICATION PROVIDERS AND GUARDS
==================================================

Configure exactly these web session guards:

- admin
- staff
- guardian

Configure matching providers:

- administrative_accounts
- staff_accounts
- guardian_accounts

Configure distinct password broker names for the three portals, but do not implement recovery endpoints or token delivery in F09.

Authentication infrastructure must fail closed:

- A pending, suspended, locked, or revoked account cannot authenticate.
- If an authenticated account later becomes non-active, the next protected request must no longer treat it as authenticated.
- An account authenticated through one guard remains anonymous to the other two guards.
- No default guard fallback may grant portal access.
- No provider may search another portal’s table.
- No account type may be passed into a different guard successfully.

Use a shared lifecycle-aware provider or middleware abstraction where appropriate, but preserve the three physical providers and guards.
